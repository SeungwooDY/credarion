# Changelog — 2026-07-31

Strict matching semantics: the engine now pairs rows 1:1 on identical
PO + material + unit price with dates inside the configured ± window;
quantity is the only field allowed to deviate. The aggregation layers
(L3 multi_delivery, L3.5 aggregate fallback) are deleted, and the AI layer
is demoted to suggest-only.

## Why

Richard's clarification of the data model: the supplier statement (对账单) is
atomic — one line per physical delivery, always. The factory clerk collapses
those lines into one ERP row only when PO, material, unit price, and date are
all identical (summing quantity), and sometimes forgets. So the engine can't
assume any consistent shape — but it CAN assume that rows on different dates
are different receipt events. The old aggregation layers summed across dates
and compared group totals, which netted away real missing deliveries (e.g.
equal totals from a 3/20 GRN and an unrelated 3/25 supplier claim were called
"matched").

## Identical-row combining on BOTH sides (`preaggregate.py`)

- Combine key is now (PO, material, calendar date, unit price) — quantity and
  amount are summed, everything else must be identical.
- **Delivery-note ref removed from the key**: two same-day atomic deliveries
  carry different DNs yet the factory keys them as one receipt; keeping DN in
  the key left the statement split while the ERP was combined.
- New `combine_erp_records` mirrors the statement-side combining, repairing
  the clerk-forgot-to-combine case. `run.total_erp` now counts combined rows
  (mirroring `total_statement`); results are stamped with
  `erp_combined_line_ids/qty/amount` and the mismatch API displays combined
  ERP totals, same as the statement side.
- After combining, each side holds at most one row per key — matching is a
  plain key join.

## Layers 1–2: date window is now a hard gate (`exact_match.py`, `fuzzy_match.py`)

Shared `run_keyed_match` core (exact = normalized key, fuzzy = loose key):

- A candidate outside ±`date_tolerance_days` (user-configurable in Settings,
  default 3) can never pair, regardless of delivery-note evidence. A missing
  date on either side is treated as unknown and does not block.
- Pass A pairs identical-unit-price rows first (a qty gap → quantity
  discrepancy); Pass B then pairs the remainder within the date window as
  price discrepancies — so a price-typo line can't steal another line's
  clean counterpart.
- Preference order within a key: delivery-note match, smallest known date
  gap, closest quantity.
- Leftovers are real missing_from_statement / missing_from_erp rows — group
  totals are never compared, so nothing is netted away.

## Deleted: Layer 3 (multi_delivery) and Layer 3.5 (aggregate fallback)

Both summed across dates. L3.5 additionally grouped across material numbers
and marked every accepted group "matched" with no discrepancy path — grabbing
at last-resort totals rather than formal logic. Historical DB rows with these
match_types still render; new runs never produce them. `_split_by_balance`
(the imbalance router) is gone with them, as is the `_date_gap_note`
match-with-note (out-of-window pairs no longer exist).

## AI layer: suggest-only (`ai_match.py`)

`run_ai_match` → `run_ai_suggestions`. Anything the AI would pair has by
definition failed the identical-fields test, so its output is no longer a
match: both rows stay unmatched (and keep counting as missing in the match
rate), and the hint is attached to each side's unmatched result as
`match_details.ai_suggestion` plus a human-readable `discrepancy_note`
("AI suggests a possible counterpart…"). Confidence threshold (0.70), batch
caps, and the `ai_layer_enabled` config flag are unchanged.

## Tests

317 passing. Deleted `test_multi_delivery.py` / `test_aggregate_match.py`;
new coverage for ERP-side combining, the date gate (incl. DN-vs-window
precedence), the no-netting scenario (equal totals across dates → 1 match +
2 missing), the clerk-forgot-to-combine repair, and suggest-only AI output.
